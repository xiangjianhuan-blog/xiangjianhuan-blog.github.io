vibe coding：画图工具（WorkBuddy）

发表于2026-11-10|更新于2026-11-10
|字数总计:4.5k|阅读时长:13分钟|阅读量:

2026 年 11 月 · 单文件 Web 应用 · 14 轮迭代 / 23128 笔操作

这个项目里我几乎没有手写过原始代码。起点是一句「做一个简洁的画图板」，终点是一个 1.44 MB 的单 HTML 文件——七种工具、七种笔刷、图层、选区变换，以及一个能把世界名画一笔一笔重放的案例库。

作品的全貌：左边是它承诺的能力，右边是它真实的界面——画布上那张《星夜》，是应用自己的笔刷一笔一笔刷出来的，不是贴图。

可以直接玩： 点这里打开画图工具（单文件应用，浏览器里双击即用，建议用电脑打开）。

一、vibe coding 究竟在做什么

流行说法里，vibe coding 是「对着 AI 许愿，然后它把东西变出来」。做过一轮长项目之后，我更愿意把它描述成把编程的重心从「实现」移到「验收」：你不再推敲某一行怎么写，但你必须非常清楚「做对了长什么样」。

这个画图工具的十四轮迭代，完整记录在 drawing-tool-prompt.md 里。它同时充当三样东西——需求台账、踩坑清单、以及可以复制给别人复刻的提示词。回头看，它比任何一次对话都更像「源代码」。

我的定义
vibe coding 的产出不是代码，是一组可被验证的现象。你描述现象，AI 负责让现象出现；现象不出现，就换描述、换路径、换证据。

真正决定成败的，是这句话里的「验证」能不能落地。画布这种东西恰好有个好处：对错是看得见的。所以整个项目里最有效的工具不是提示词技巧，是截图——把页面丢进无头浏览器，截一张，自己看，再决定下一句说什么。

二、系统描述：一个文件的架构

整个应用是一个 HTML 文件：CSS 与 JS 全部内嵌，双击即开，没有构建、没有依赖、没有后端。唯一可选的外部资源是一段 CDN 上的笔迹平滑库，加载失败会自动降级到内置引擎——所以断网也能画。

设计决策 说明
01 单文件交付 1.44 MB / 一个 .html。可以直接发邮件、丢 U 盘、贴到任何静态托管上，不需要「部署」这个概念
02 固定文档坐标系 画布固定 1600×1000 逻辑像素，屏幕坐标经 toLogical() 换算；缩放只改 transform，不碰像素
03 零后端 保存 = 合成可见图层导出 PNG/JPG；主题、案例数据全部在文件内或 localStorage
04 高清自适应 所有图层 canvas 按 devicePixelRatio（上限 2）放大再统一 setTransform，高分屏不糊

三层画布，各管一件事

结构上最关键的决策是把「正在画的东西」和「已经画完的东西」分开。页面里其实叠着三组 canvas：

层 承载 为什么单独一层
图层 canvas 每个图层一张，内容永久落盘 图层可增删、排序、显隐、单独导出
strokeCanvas 正在拖动的这一笔 抬笔时才按整笔透明度合成，笔画内重叠不会叠深
shapeCanvas 图形、钢笔预览、选区框与手柄 手柄、虚线框属于「界面」，不能被存进画里

这个分层是第二轮迭代时被迫做的：右键拖动时笔宽预览环不跟随光标。原因很朴素——监听挂在元素自己身上，光标一出界就丢事件。改成监听 document 的 pointermove 后一切正常。经验是，光标类的问题多半出在事件边界，不在渲染。

状态与历史的形状

所有 UI 状态收敛到一个 state 对象（当前工具、颜色、笔宽、透明度、线型、笔刷、图形类型……），切换工具统一走 setTool()，而它做的第一件事是 finalizePending()——把没落地的图形、文字、钢笔、选区先提交掉。这个「切换前先落地」的约定，消灭了一大类「切工具后画的东西消失了」的 bug。

历史是快照式的：每次改动画面前记录所有图层的 toDataURL 与图层结构，栈上限 40 步。代价是内存，收益是增删图层、换序、显隐这些结构性操作也能被撤销——而它们恰恰是最容易被撤销逻辑漏掉的。

三、笔迹引擎：印章、里程与预览层

最难缠的部分是笔刷。最初的实现是 ctx.stroke() 描边，结果实线总有缺口，七种笔刷也只有尺寸差别。第六轮彻底换掉：改为印章引擎。

每种笔刷先用 128×128 的离屏 canvas 画一张笔尖蒙版——径向渐变、鬃毛缝隙、蜡笔颗粒、水渍边缘——再用 source-in 把它染成当前颜色，按「笔刷类型 + 颜色」缓存。绘制时沿鼠标轨迹按固定间距反复盖章，用一个 carry 变量记住「这一段走完了多少里程、还欠多少」，保证跨帧连续、断笔不断线。

为什么不用 setLineDash？因为它和印章天生冲水——虚线是描边的概念，印章没有「路径」可循。改成累计里程后，实线、虚线、点线在同一套代码里统一了。

一个反直觉的坑

橡皮擦绝不能走预览层。最初按下时照常先画到 strokeCanvas，再用 destination-out 合成，结果拖动时画出一条黑线——因为预览层本身是透明黑。正确做法是按下那一刻直接擦图层，边走边擦。

笔尖缓存也有代价：颜色一变就要重建蒙版。做临摹功能时一张画里出现两千多种颜色，缓存被反复击穿，导入会卡到十几秒。解法是把颜色量化到 72–88 色的调色板并做吸附，缓存上限提到 256 并改成批量淘汰——同样的画面，导入时间回到两秒级。

四、功能描述：七种工具与它们的手感

把十四轮需求摊开，它已经不是一个「画图板」，而是一个小型绘画应用。下面按模块列一遍实际能做的事，以及每件事在实现上到底动了什么。

模块 能做什么 实现要点
画笔 7 种笔刷：圆形、方形、书写笔、毛笔、油画笔、蜡笔、水彩；笔宽 1–80，透明度 0–100，实线/虚线/点线 印章引擎 + 笔尖蒙版缓存；书写笔与毛笔在实线下改走压感轮廓（首尾收笔、笔宽随速度 1.2→0.55 倍变化）
橡皮擦 硬边擦除，可调大小，光标显示为虚线环 destination-out 直接作用于图层，跳过预览层；专用无渐变笔尖，间距压到 0.06×笔宽 避免扇贝边
图形 8 种：矩形、圆角矩形、椭圆、三角形、菱形、五角星、直线、箭头；支持填充 模型是「中心点 + 宽高 + 旋转角」；选中后 8 个手柄改尺寸、顶部圆点旋转（Shift 吸附 15°），手柄尺寸按 1/缩放 反算
文字 画布内就地多行编辑；9 种字体、字号 8–300、左中右对齐、粗体/斜体/下划线/删除线 点击处浮出 textarea，随画布缩放重新布局；样式改动同时作用于「正在编辑」与「已选中」的文字
钢笔 贝塞尔曲线，拖拽拉出对称手柄，点回起点闭合 闭合只描边不填充——内部保持透明；悬停时实时预览下一段
油漆桶 点击填色，容差 32，遇线条自动停下 扫描线洪水填充，只填与落点连通的区域；同色区域幂等跳过

图层 多图层、重命名、拖拽排序、显隐、缩略图、批量删除 每层独立 canvas；HTML5 drag & drop + 蓝色落点线；缩略图 48×30 实时重绘

系统能力 撤销/重做 40 步、缩放 0.1–8、深/浅主题、PNG/JPG 导出、全局快捷键 快照式历史；滚轮以光标为锚点缩放；主题走 CSS 变量 + 首屏内联脚本防闪白

真实界面。画布上是案例《星夜 · 临摹梵高》，右侧三个图层由 夜空·星辰与漩涡、山峦·村舍与教堂、柏树与近景山岗 组成，可以单独隐藏任意一层看它是怎么堆出来的；当前缩放 69%。

界面本身没有花活：吸顶工具栏放工具、颜色、笔宽、透明度、线型、笔刷；二级设置条做成浮层，切到对应工具才出现，不挤占画布；右侧是图层面板，右下角是缩放条，底部一行常驻快捷键提示。做减法的地方比做加法的地方多——比如把「多选」按钮从新建旁边拿掉，改成「选中了图层才出现批量删除」，工具条立刻安静下来。

五、案例库：把画作存成可回放的操作

这是整个项目里我最满意的一部分，也是最「vibe」的一步：需求是「加入成品案例，必须是用这个平台现有功能画出来的」。

贴一张图片上去很容易，但那不叫案例，那叫壁纸。真正的做法是：案例不是像素，是操作。每个案例被写成一组 ops，跟撤销栈、跟用户手绘，用的是同一套语言：

导入一个案例，就是把这几千条指令按图层顺序喂给 playOps()，让真实的笔刷引擎重新盖一遍章。好处是荒谬的实在：画可以撤销、可以擦、可以放大到 800% 看笔尖纹理，因为它本来就只是一堆笔迹。

导入《蒙娜丽莎 · 临摹达芬奇》后的画面，底部一条提示：已导入 · 3 个图层。右侧 面容·发丝与五官、人物·衣袍与手、远景·雾霭山水 各自是独立可编辑的图层——关掉最上面那层，脸就退回成一块块色斑。

目前库里六个案例，故意拉开风格：油画三张（梵高、达芬奇、莫奈）、主题性油画一张（开国大典）、水墨青绿一张，再加一张完全由几何与平涂构成的原创浮世绘。命名沿用同一套规范——作品名 · 临摹作者 或 作品名 · 原创，标签写 技法 · 特征，图层固定三层。

六、临摹是怎么被「算」出来的

第一阶段我走错了路：用三角形、椭圆、矩形去「拼」造型。出来的东西像是插画而非绘画——形状对，气质全无。第二版换了个思路：不复刻形状，复刻笔触。

  1. 映射：参考图等比铺到 1600×1000 的文档坐标里，算出裁切范围，避免拉伸变形。
  2. 量化：中位切分把颜色压到 72–88 色（不抖动），每个取样点吸附到最近的调色板色——这一步是为了让笔尖缓存活得下去。
  3. 定方向：对灰度图求结构张量，得到每个像素的笔触走向与「方向一致性」。一致性高的地方（发丝、树影、浪脊）拉长笔触，低的地方（天空、肌肤）用短笔触平铺。
  4. 落笔：按网格逐格取样，每格生成一笔，长宽由方向场与细节密度决定，颜色取格内均值，交给真实笔刷引擎盖章。
  5. 打底与收边：最底层先铺一遍不透明度 100% 的底色，否则笔触之间会漏出白纸；最顶层用图形工具的矩形补边框或画布边缘。

顺序和分组也有讲究：三个图层不是随便切的，而是按「视觉层次」分——远景、主体、细节。这样导入之后，用户关掉某一层就能看到这幅画是怎么一层层长出来的，这比一张成品图有价值得多。

踩过的坑（每一条都是靠看图发现的）

  • 白缝：笔触间距大于笔宽就会漏底，用洋红纸底跑一遍，数洋红像素占比才确认真的补干净了。
  • 竖条纹：油画笔的笔尖蒙版有竖向鬃毛缝，大面积平涂时会变成栅栏，大色块必须换圆头笔。
  • 马赛克感：单一尺度取样一定像拼豆，改成粗细两套尺度按羽化概率混合，边界才不显。
  • 底色盖住细节：每层都打底会把邻层的细节糊掉（《星夜》中间出现一条横向污带），打底只能在最底层做一次。

七、十四条经验里留下的七条

把那份文档里的十四轮拉平来看，能复用的其实只有七条。它们都不关于提示词怎么写，而关于怎么和「看不见屏幕的合作者」协作。

1. 描述可验收的现象，不描述功能名

「实线有缺口」是可验收的，「优化笔刷质量」不是。前者一轮能改完，后者能来回五轮。

2. 每轮只动一件事

同时改笔刷和图层，出问题时你分不清是谁的锅。这个项目里每个卡住的阶段，都是因为前一轮塞了太多。

3. 必须给 AI 眼睛

它看不见画面。无头浏览器截图 + 像素统计（「洋红占比 0.008%」）比任何形容词都管用。整个项目最有价值的调试工具就是这两样。

4. 卡住时换路径，不要打补丁

浮世绘那张画的浪体改了十四版。前十一版都在修同一个多边形扫描填充的边角；真正解决问题的是承认这条路不对——改成平涂 + 轮廓走一遍本色收边。识别「该换路了」的信号是：同样的 bug 第三次出现。

5. 让功能吃自己的狗粮

案例库必须由应用自身能力生成，所以它不是贴图，是可回放的操作序列。约束越硬，设计越干净。

6. 文档是上下文，对话不是

十四轮之后对话早就装不下了。真正让项目能继续的是那份 prompt 文档：结构约定、坐标约定、改动守则、自检清单。新开一个会话，喂它这份文档，就能接着干。

7. 单文件是 vibe coding 的天然容器

没有构建、没有依赖树、没有环境差异意味着反馈回路只有一个动作：刷新。代价是文件会膨胀到 1.4 MB，收益是它至今仍然双击就能跑。

一句总结
vibe coding 里，AI 不缺写代码的能力，缺的是「知道你满意了没有」的判据。判据是人的工作——把它写清楚，剩下的才是许愿的部分。
