vibe coding：黄昏海岛1.0（WorkBuddy）

发表于2026-11-13|更新于2026-11-13
|字数总计:4.1k|阅读时长:13分钟|阅读量:

2026 年 11 月 · 单文件 Three.js 世界 · 6710 行 / 69 个模型 / 6 种天气

这次不是一个新项目，而是一次连环改造。起点是一个看起来很傻的问题：双击 index.html，船在，海在，树不见了。

终点是现在这个样子——一座会入夜、会下雨、会起雾的岛，脚下还有一片能潜下去的海。

可以直接玩： 点这里打开「黄昏群岛」（建议用电脑打开；点击画面锁定鼠标，WASD 移动，Shift 加速，Ctrl 下潜；按 2-5 拿起乐器后，按住左键演奏，松开换下一首曲子）。

一、第一个 bug 不在代码里

「树没有渲染，有好多资源都没有渲染。」

如果只看这一句，最容易走的路是去查植被生成逻辑。但真正的原因在浏览器协议里：页面是用 file:// 双击打开的，而 Chrome 同源策略会拦掉所有 fetch / XHR——GLTFLoader 加载 GLB 走的正是这条通道，失败还是静默的。岸上的岩石、灌木、道具全是 GLB，于是它们集体消失，只剩程序化生成的地形和船。

树不是没生成，是没能被读进来。

这件事值得单独记一笔：「渲染不出来」和「没渲染」是两个完全不同的问题，而 AI 很容易顺着用户的措辞去改前者。判断方法很简单——打开控制台。一旦看到一串 Access to fetch ... has been blocked by CORS policy，就不用再动场景代码了。

最后的处理是两条腿走路：页面检测到 file:// 时直接弹一张引导卡，说明要用本地服务器；同时给一个 start.bat，优先调 Python，没有就退回 PowerShell 自带的 HttpListener。零依赖，双击即用。

第一个教训
用户描述的是现象，不是病因。「树没渲染」这句话里，没有任何一个字指向 CORS。

二、树为什么长在沙滩上

第二个问题同样是「现象」：山上光秃秃，沙滩上一堆树。

原来的植被撒点用的是全岛均匀采样，再用高度做一点粗筛。问题在于——它筛的是「这个点能不能放」，而不是「这个点该放什么」。沙滩、山腰、山顶在同一个池子里竞争，随机数当然不会替你想美学。

改造的办法是把「高度带」变成硬约束，每种植物只在自己那一段高度里出现：

高度带 该长什么 实际布置
沙滩 1.0–3.4 m 棕榈，且要成扇 高棕榈 10 + 半高棕榈 9，另在出生点手动补了几棵做框景
山腰 3.4–5.0 m 疏林、灌木、蕨 小树 34、圆灌木 70、蕨丛 110
山顶 5.0 m 以上 密林 岛屿树 24 + 橡树 23 + 白桦 17
全岛地被 草与花 草丛 880 + 120、高草 200

数字之外还有一个细节：近景需要手工。纯随机的密林远看很壮观，走近了会觉得假——所以出生点附近的那几棵棕榈是手摆的，用来在玩家转身的第一眼框住海面。

三、换船：把甲板「量」出来

原本的船是程序化拼的——一块块木板、一根根桅杆。换成 CC0 模型之后，视觉上立刻不一样了（43k 三角面，带索具、帆、舷炮），但马上撞上一个很具体的问题：

玩家站在哪？

模型是别人做的，我不知道甲板在哪个高度。硬编码一个数字，人就会浮在甲板上方或者陷进去。

解法是让代码自己去测：模型加载完成后，从船体上方沿船长方向打 21 条射线，向下打中船壳网格，把命中点高度记进一张表 SHIP_DECK_TAB[21]，玩家行走时按位置插值查表。

顺带还有两个必须处理的点：模型船首朝 +X，而船的航行逻辑朝 +Z，所以外面要包一层 Group 转 -π/2；吃水深度也要跟着模型改，最终 ship.position.y = -2.6。

可迁移的做法
当「外来资产」和「自有逻辑」对不上时，别猜参数——让运行时自己去测量，再把结果存成表。射线、包围盒、顶点采样都是廉价的测量工具。

四、把镜头沉下去

这是整轮改造里最大的一块。它不只是「加一个水下滤镜」，而是要在同一个场景里再造一个世界。

海底要和岛「接得上」

最怕的效果是：游到岸边往下看，海底和沙滩之间有一道缝。所以海底高度函数 seabedHeight(x, z) 在近岸区直接复用岛屿地形的解析式，与水面下的岛坡完全同一条曲线；远海再过渡到 -23 米的平原，叠沙丘噪声、四组礁石高斯凸起，再挖一条海沟。两边公式一致，重叠区就不会穿模。

生态不是撒点，是分层

海底的东西按「离岸距离 + 深度」分层摆：岸坡是海带（90 株，避开航道）、远海是海藻林（18 丛）、浅水是珊瑚坪（珊瑚头 30 + 海扇 8）、深处是岩拱、章鱼礁、气泡柱。贝壳和沉船残骸留在沙地上做叙事。

鱼不是一条条摆的，是五群：金枪鱼 22 + 14、梭鱼 18 + 12、鬼头刀 8。全部用 InstancedMesh，每帧在 JS 里组合矩阵让它们绕群心环游；尾摆则交给顶点着色器——按 instanceMatrix 的平移量算相位，让每条鱼的摆动错开，看起来才不像同步的机械鱼。

水下的「质感」由四样东西叠出来

元素 做法 少了它会怎样
斯涅尔窗 相机在水下时，海面着色器切到仰望分支，画一片亮天窗 抬头是平的蓝，没有「在水里」的直觉
焦散 用噪声生成光斑，乘上环境强度 uCauEnv 沙底死板，像塑料
悬浮颗粒 相机周围的点云，圆形软点 水太干净，失去体积感
折射后处理 EffectComposer 加一个 UV 波动的 ShaderPass 水下画面太「锐」，像隔着玻璃拍

后处理这条链是常开的：RenderPass → 水下折射 → OutputPass，色调映射统一放在末端。常开是有原因的——如果按需开关，下潜那一瞬间所有材质都要重编译，会卡一下。

深度决定能见度：越深雾越浓越暗，暴风雨时再乘一个 vis 乘子，能见度骤降。这是玩家唯一能「感觉到深度」的通道。

五、昼夜与天气：把美术变成一张参数表

「黄昏很好看，但我想让它会天黑。」

如果按字面实现，很容易写成一堆 if (hour > 18) 变暗。真正可行的做法是把美术判断翻译成参数表，再让代码只负责插值。

9 个关键帧

DAY_KEYS 存了 9 个时刻的完整快照：太阳颜色与强度、天顶/中天/地平线三段天空色、地面反照、雾色与雾密度、浅水/海水/深水三档水色、焦散强度、半球光强度、曝光。

每帧只需在两帧之间插值，输出一组当前值。天空、海面、焦散、雾、灯光全部从这一组值读数——只有一处真相。

6 种天气 = 11 个乘子

天气不重写一套渲染，只提供乘子：云量、阳光衰减、雾倍率、浪高、泡沫、涟漪、雨量、风力、焦散、能见度、饱和度。

关键在过渡：WEATHER.cur 每帧向 target 做 lerp，所以切天气不会硬切，云是慢慢压过来的，浪是慢慢起来的。

还有一个容易漏的细节：浪高必须两边同步。着色器里的 uWaveGain 和 JS 里的 WAVE_GAIN 要写同一个值，否则船会浮在「看得见的浪」和「算出来的浪」之间——视觉上就是船在穿模。

六、六个翻车现场

这一节是这篇文章里我认为最有价值的部分。它们都不是「不会写」，而是「没想到」。

1. 常量声明顺序 → 整个模块不执行

SHIP_DECK_TAB 用 SHIP.DECK 做初始值，但 SHIP 写在它下面。const 的暂时性死区让它直接抛 ReferenceError，而模块顶层一抛错，后面所有代码都不执行——表现为页面停在加载页。

教训：顶层抛错 = 全盘不执行，报错信息往往只指第一行，别被它带偏。

2. 函数被困在块作用域里

绳梯的构建函数写在了 if (!USE_MODEL_SHIP) { ... } 的大括号里面。换成模型船后，装配阶段要从外面调用它，于是 buildShipLadder is not defined。

这类问题在「用开关切换新旧实现」的重构里特别常见——旧代码被包进 if，但它导出的东西还有人要用。

3. 着色器用了新 uniform 却没声明

海面 fragment 里加了 uUnder、uNight、uFlash，但 GLSL 顶部忘了 uniform float 声明。表现是材质编译失败，整片海变成纯色或者干脆不显示。

教训：改着色器时，uniform 声明和 JS 侧赋值要成对检查。

4. 夜晚的海水是青绿色的

这是最有意思的一个。夜晚的天空对了、灯光对了，但海面依然泛着一层青绿的光。

原因不在海面：太阳的方向在夜里依然在地平线之上。仰角公式只用了正弦的正半周，elev = 0.12 + max(0, sin) * 0.72——夜间被 max 钳在 0.12，太阳等于永远挂在地平线上一点。于是次表面散射和镜面高光整夜都在工作。

修复是两步：让太阳真正落到地平线以下（仰角取负），再把海面的太阳相关项统一乘上 uSunVis（夜晚和阴天自然归零）。

数值系统的第一性
「夜晚太亮」不要去调亮度参数。先问：这个系统里，夜里应该还有太阳吗？

5. 夜空里的白色方块

夜晚截图里，天上飘着几个边缘锐利的白矩形。排查过程比较曲折：先怀疑云、再怀疑海鸥、再怀疑光柱 Sprite，逐个隐藏都还在。最后用射线从白块的屏幕坐标反查，命中距离 4183——那是天球。

问题在星空实现：按方向做哈希网格撒星，但把整个网格单元涂白了，没有在单元内做点形状。于是每个命中的 cell 就是一块白色矩形。

6. 乐器「怎么点都不响」：一行代码的前提变了

发布之后试玩，最先暴露的不是画面，是乐器：怎么点都演奏不了。

第一反应是查 WebAudio、查事件绑定，都没有问题。真正的原因藏在指针锁定里：

  • 游戏用的是 PointerLockControls(camera, document.body)，锁定的是 **document.body**；
  • 指针锁定期间，所有鼠标事件的 target 都会变成被锁的那个元素——也就是 body；
  • 而点击监听里写着 if (e.target !== canvas) return;——锁定后这个条件永远为真，演奏永远触发不了。

这行代码在锁定之前是完全正确的。它没有写错，是它的前提变了。修法是把「精确匹配 canvas」换成「判断是否点在 UI 控件上」：

顺手把交互模型也改成了更符合直觉的形态：按住左键持续演奏，松开即停；每次停下后，下一次演奏自动切到下一首——四首全部由 WebAudio 实时合成的曲子（海盗的黄昏 / 酒馆小调 / 起锚谣 / 风暴船坞）按顺序循环，依然零音频文件。

这条最值钱
很多 UI 事件的诡异 bug，本质都是「某个前提悄悄变了」。代码没改，环境改了。排查时不只问「这行代码对不对」，还要问「它的假设还成立吗」。

七、上线时的两个坑

做完之后想放到博客上。直觉是「纯静态，扔进 source/ 就行」，实际有两个坑。

第一个：不配 skip_render，页面会被博客吃掉。 Hexo 会把 index.html 当成一篇文章，套上主题的 layout，生成一个外壳——游戏当然跑不起来。实测构建出来的产物里，页面标题变成了站点标题，正文被塞进了 meta description。

第二个：skip_render 配错，构建直接报错。 Hexo 7 的默认 _config.yml 里本来就有一个空的 skip_render: 键。往文件末尾再追加一个同名键，YAML 解析器立刻抛 duplicated mapping key。

部署是另一门学问
本地跑得通不等于线上跑得通。差异往往不在代码，在环境：协议、路径、构建器的默认行为。

八、这次留下的几条

1. 先分清「没渲染」和「渲染失败」。
一个控制台截图能省掉半小时的场景代码排查。

2. 外来资产要对齐，就现场测量。
甲板高度不猜，打射线测；船头朝向不对，包一层 Group。把测量结果存成表，后面所有逻辑都查这张表。

3. 让美术判断变成参数表，代码只负责插值。
9 个关键帧 + 6 组乘子，比一堆 if (hour > 18) 好维护一百倍，也让「加一个天气」变成填一行数据。

4. 数值不对，先问物理，再调参数。
夜晚的海发绿，是因为太阳没落山；不是因为水色不够暗。

5. 屏幕上多出来的东西，用射线反查，不要逐个试。
像素 → NDC → Raycaster，一次就能问出「你是谁、多远、什么材质」。

6. 验收要靠眼睛。
整个项目里最有效的工具是截图：把页面丢进无头浏览器，按不同时刻、不同天气、水上水下各截一张，自己看。能看见的错误，才改得动。

7. 部署前先在真实环境构建一次。
hexo generate 跑一遍、比对产物，比读十篇部署教程都管用。

附：资产、许可与文件

在线游玩： 黄昏群岛 · Dusk Isles

说明
交付形态 单个 index.html（6710 行 / 284 KB）+ assets/models/（75 个 GLB / 26 MB）
运行时 Three.js r169（ESM + importmap，jsDelivr CDN），无构建步骤
模型来源 3DAssets.dev、Poly Haven，全部 CC0，可商用；共 75 个 GLB
程序化内容 地形、海底、海水、天空、云影，全部由代码生成
部署 静态托管即可（本页链接为云端托管；也可放进 Hexo 的 source/ship/ 随博客发布）

最后说一句题外话。这次改造里，我几乎没有逐行写代码，但每一轮都在做同一件事：把「我觉得不对」翻译成一句 AI 能执行、且我能验收的描述。「树不应该长在沙滩上」是一句审美判断；翻译成「按高度带分配物种，山顶密度 3 倍于山腰」之后，它才变成可以执行的指令。

vibe coding 的门槛不在提示词，在于你有没有能力把眼睛看到的问题，拆成系统里可以定位的那一层。
